# Executive Overview storytelling and UX

## Purpose and audience

The Executive Overview is a fast, evidence-led entry point for business and
analytics readers investigating MercadoLibre's financial, operating,
ecosystem, and macroeconomic context. It answers: “What does the current
evidence say about MercadoLibre's business, ecosystem and operating context?”
It does not answer what the company should build.

## Storytelling

The page uses a clear storytelling sequence: **Context → Status → Evidence →
Interpretation → Next exploration**. Context identifies the scope of MELI
Intelligence. Status summarizes dataset coverage and freshness. Evidence
shows a small selection of reported signals. Interpretation presents only
interpretations already available in the Evidence layer. Next exploration
points to Data Quality & Sources for coverage and lineage details.

Signals come from an explicit allowlist of metric IDs present in the current
financial facts, operational KPIs, and macro datasets. Values, units, periods,
and source labels come from the data. The UI does not calculate growth,
margins, or other analytics. Missing values remain unavailable; they are
never replaced with zero or synthetic data.

## Progressive disclosure

The initial view contains only executive context, freshness, dataset
coverage, and a few reported signals. Details appear below the fold or in
expanders and secondary sections. Technical tables and complete source
lineage do not compete with the main narrative, but users can open them when
deeper inspection is useful. This progressive disclosure reduces cognitive
load and supports recognition over recall and an aesthetic, minimalist
design.

## Nielsen heuristics

The page applies Nielsen heuristics through visible system status (available
dataset count, latest reference date, and degraded-state messages), business
language, reversible shared filters with a reset action, and consistent
status and date formatting. Shared filter validation prevents invalid date
ranges. Labels, units, periods, and source context make signals recognizable
without requiring users to remember internal metric IDs. A small summary
comes first, with details available on demand. Missing, empty, invalid, or
unreadable data has a clear non-blocking explanation and a path to Data
Quality & Sources. Short captions provide context where needed.

## Accessibility

Meaning never depends only on color: dataset states have explicit text
labels, including `AVAILABLE`, `MISSING`, `EMPTY`, and `INVALID`. Labels are
explicit, text is short and understandable, and the visual design should
maintain adequate contrast. Status may use an icon or color as a secondary
cue, but it always remains identifiable in text. Status colors do not
represent good or bad business performance.

## Freshness

The latest available reference date remains visible in the overview and
dataset-level freshness is shown in Data Quality & Sources. A reference date
describes the period represented by the data; retrieval time is not presented
as economic freshness. Older observations must remain visibly dated and must
not be styled or described as current merely because they are the latest
available locally. Missing freshness is shown as unavailable, never inferred.

## Evidence vs Interpretation

Reported metrics are presented as evidence with their reference period and
source. Existing records of type `INTERPRETATION` are explicitly labeled as
interpretation and retain their metric, source, date, and evidence ID. An
interpretation is not a fact, and the UI does not create or upgrade evidence
into interpretations. No causal claim, forecast, score, or recommendation is
generated by the page.

## Product Evidence

When Product Evidence is available, the overview may show counts of
investigative hypotheses and discovery questions. These are not business
KPIs: hypotheses express uncertainty and questions invite validation.
Neither is a fact, recommendation, or product solution, and the UI does not
turn them into certainty about user behavior.

## Availability and recovery

Dataset health uses the shared `AVAILABLE`, `MISSING`, `EMPTY`, and `INVALID`
states. Missing, empty, invalid, or unreadable data produces a visible,
non-blocking explanation. Data Quality & Sources shows status and freshness
in its main table; full file paths and source lineage are available in
per-dataset details. The interface never repairs or rewrites an invalid
file.

Dates use one consistent day-month-year display. The sidebar provides
business-domain and date filters with a reset action. Filters use the shared
filter and data-access contracts; datasets without a relevant field remain
unchanged. The first view has at most four selected evidence signals and no
large raw table. No chart is required in this slice. Future charts must answer
a specific question; pie, donut, gauge, radar, 3D, and decorative heatmaps are
excluded. Signals include a period and reference date, with source and value
as loaded available in details.

## Data access and limitations

The entrypoint delegates to shared catalog, health, filter, and query/data
access modules. Page renderers select and present existing rows; they do not
import source clients, pipelines, analytics/strategy builders, or storage
writers. No global mutable DataFrames or synthetic fallback are used.

The overview is intentionally not a full Financial, Commerce, Fintech, Macro,
PESTEL, SWOT, or Product Evidence dashboard. It does not show valuation,
causal analysis, forecasts, scores, priorities, or recommendations. Future
navigation can add domain dashboards, PESTEL, SWOT, Product Evidence, and
valuation when those views are scoped separately.

Run locally with `streamlit run streamlit_app.py`. Pure presentation helpers
are unit-tested without starting a Streamlit server; no browser automation is
required for this slice.
